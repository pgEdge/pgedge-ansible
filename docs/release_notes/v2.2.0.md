# v2.2.0

These notes describe the changes in v2.2.0, the release after v2.1.0.
The [Changelog](../CHANGELOG.md) summarizes them.

## Overview

Changes to `db_names` now reach a running cluster. A database added to the list
is created on every node and joins Spock the next time the deployment playbook
runs, including on an Ultra-HA cluster whose leaders Patroni has moved off each
zone's first node. Removing a database from the list no longer shrinks the
worker and slot pools the cluster may still need.

A cluster that already holds data can now grow by a zone while it runs, on
simple and Ultra-HA clusters alike. The new zone's hosts go in the inventory,
and the deployment playbook runs with `-e pgedge_join_zones=<zone>`. The zone
copies every database from an existing zone and receives every write the other
zones make during the copy, with nothing lost or applied twice, while those
zones keep taking writes. Before the copy, the run may restart the existing
zones one node at a time to enlarge their worker and replication pools. A new
`remove_zone` role takes a zone out of the cluster again. See
[Adding a Zone to a Running Cluster](../add_zone.md).

A zone in an Ultra-HA cluster can now grow while it runs. A node added to the
inventory with an existing zone's number joins that zone as another replica the
next time the deployment playbook runs.

Running the deployment playbook again against a deployed cluster now changes
nothing and reports nothing changed, whether or not Patroni has since moved a
zone's leader, and the end-to-end tests hold every deployment to that.

pgEdge's package repositories now authenticate clients with a certificate.
`install_repos` installs the certificate given in the new client certificate
parameters, and `pgedge-subscription-manager` enables the repositories with it.

## Upgrading from v2.1.0

Hosts that install from pgEdge's own repositories need a client certificate
and its key. Set `pgedge_client_cert` and `pgedge_client_key` to their PEM
contents, or `pgedge_client_cert_src` and `pgedge_client_key_src` to files on
the controller; see
[Client Certificate for the pgEdge Repositories](../roles/install_repos.md#client-certificate-for-the-pgedge-repositories).
Without them, `install_repos` installs `pgedge-release` with its repositories
disabled, warns, and no pgEdge package installs. Hosts that install from a
`repo_url` of the site's own need no certificate, but the host that builds
that mirror from pgEdge's repositories does.

Otherwise, playbooks and inventories written for v2.1.0 need no changes,
unless they set `db_names` to different lists on different pgEdge nodes.
`init_server` now refuses that; set `db_names` once, on the `pgedge` group.

Running the playbooks with `--limit` is not supported, and the
[Execution Strategy](../configure_playbook.md#execution-strategy) section now
says so. Every run should cover the whole inventory. A run whose `--limit`
leaves out a zone's primary now stops rather than skipping the writes to that
zone, and `setup_pgedge` stops unless it can read the Spock state of every
zone. These checks are safeguards, not a supported way to limit a run.

A run now stops, before it creates anything in Spock, when the inventory lists
a zone that is not part of a cluster that already holds data. Previously such
a run subscribed the zone without copying the data, and the zones disagreed
from then on. Pass `-e pgedge_join_zones=<zone>` to join the zone, or take its
hosts out of the inventory. A run also stops when the zones that are part of
the cluster are not all subscribed to each other.

`pgedge_seed_zone` is for recovery only, and a run refuses it together with
`pgedge_join_zones`. The recovery playbook is unchanged.

Joining a zone needs Spock 5.0.9 or later on every zone, and the joining zone
may not run an older major or minor Spock release than any member. Running the
deployment playbook again does not upgrade Spock on a zone that is already
built, so upgrade any older zone by hand before a join.

## Changes

### Added

- A zone can join a cluster that already holds data, on simple and Ultra-HA
  clusters, while the other zones keep taking writes. Add the zone's hosts to
  the inventory and run the deployment playbook with
  `-e pgedge_join_zones=<zone>`; a comma-separated or JSON list joins several
  zones one at a time. Previously a zone added to a running cluster was
  subscribed to the others without any of the data they held. (EE-45)

    `setup_pgedge` follows Spock's zero-downtime add-node procedure. For each
    database, the joining zone copies an existing zone's roles, schema and
    data. Every other zone keeps the writes it makes during the copy in a
    replication slot, and the joining zone reads them from the point the copy
    reached, so no write is lost or applied twice. If the source zone's apply
    workers cannot be paused, the join warns and goes on, and writes from up to
    a second before the copy may then be applied twice. Every zone then
    subscribes to every other. Before it changes anything, the join checks each
    zone's Spock release, the worker and slot pools, that every existing
    subscription is replicating, and that the joining zone is empty.

    A join that stops partway resumes when the same command runs again. The
    joining zone records an unfinished join in the `pgedge.join_pending`
    database setting until it replicates with every member. A join that cannot
    be resumed releases what it held on the other zones and says to run
    `remove_zone` and join again. The new `pgedge_join_wait_minutes`, `30` by
    default, limits each wait for a bookmark. See
    [Adding a Zone to a Running Cluster](../add_zone.md) and
    [setup_pgedge](../roles/setup_pgedge.md#joining-a-zone-to-a-running-cluster).

- The new `remove_zone` role and `sample-playbooks/remove-zone` playbook detach
  one zone from a running cluster, either to retire it or to start a failed
  join over. A run needs `-e remove_zone=<zone> -e remove_zone_confirm=true`.
  It refuses to start when another zone's primary cannot be reached, or when
  the zone holds the only complete copy of a database. (EE-45)

    When the zone can be reached, the role first waits, up to the new
    `remove_zone_wait_minutes` (10 by default), for every other zone to apply
    all of the zone's writes, and stops with nothing changed if one does not.
    Every other zone then drops its subscriptions, replication slots, Spock
    node and `spock.progress` rows for the zone. The zone, when it can be
    reached, drops its own subscriptions and, last, its databases in
    `db_names`, which the next deployment run creates again empty. A run that stops partway is finished
    by the next. See [remove_zone](../roles/remove_zone.md).

- The end-to-end tests add zones to a deployed cluster and remove them: two
  more zones on a simple cluster, or a third on Ultra-HA, while a writer
  inserts rows on every existing zone. `tests/verify/verify-zone-join.yml`
  checks that every zone ends with the same rows, the full subscription mesh
  and no replication conflicts. The Simple Cluster and Ultra-HA workflows gain
  a `zone-join` job, whose `zone_join` input chooses how much it runs: (EE-45)

    - `basic`, the default, runs the main path: joins, one of them stopped
      and resumed, a run refused without the flag, and `remove_zone`.
    - `full` adds every refusal, interruption and variant, such as a copy that
      dies partway, a rebuilt zone the others still subscribe to, and
      `remove_zone` against a zone that is down.
    - `off` skips the job.

    Under act, the workflows run only the `test` job unless given
    `--input act_job=zone-join`. `tests/zone-join-scenarios.sh` runs each
    scenario locally.

- A node added to the inventory of a running Ultra-HA zone now joins the zone
  when the deployment playbook runs again. Previously `setup_etcd` started the
  new node's etcd as though bootstrapping the zone, and the running members
  refused it. The role now adds the node as an etcd learner, promotes it once
  it has caught up, and restarts the zone's members one at a time to list it.
  Nodes join one at a time, and a run stopped partway through a join is
  finished by the next. See
  [Joining a Running Zone](../roles/setup_etcd.md#joining-a-running-zone).
  (#67)

- The Ultra-HA end-to-end tests add two nodes to zone 1 and check that etcd,
  Patroni and replication include them, and that a second run changes nothing.
  One node is first left as an unpromoted learner, as an interrupted join
  would leave it. (#67)

- The new `zone_primary` task file in `role_config` records the node running
  each zone's primary as the `zone_primary` fact: the zone's only node on a
  simple cluster, and Patroni's leader on Ultra-HA. It stops the run unless
  the zone has exactly one leader that every node agrees on, and the primary
  is among the play's hosts. `setup_postgres`, `setup_pgedge` and
  `finalize_backrest` use it to choose where to write. With
  `zone_primary_read_only`, which `remove_zone` sets, it never starts Patroni
  and records an empty fact rather than stopping. See
  [Zone Primary](../roles/role_config.md#zone-primary). (EE-44, EE-45)

- The new `sizing_floor` task file in `role_config` reads the worker and slot
  pool sizes each zone was last configured with into the `pg_sizing_floor`
  fact. The calculated sizes never go below it. See
  [Sizing Floor](../roles/role_config.md#sizing-floor). (EE-44)

- The new `unmanaged_db_names` parameter lists databases that run on the
  cluster but that the collection does not manage, such as one removed from
  `db_names` that still replicates. The worker and slot sizing counts them,
  and the collection does nothing else with them. See
  [unmanaged_db_names](../configuration/cluster.md#unmanaged_db_names).
  (EE-44)

- `init_server` refuses an inventory whose pgEdge nodes do not all list the
  same databases in `db_names`, or in `unmanaged_db_names`. Spock subscribes
  each database to the same database on every other node, so the lists must
  match; their order does not matter. (EE-44)

- `install_repos` installs a client certificate for pgEdge's package
  repositories, which now authenticate clients with mutual TLS. The
  certificate and key are given inline in `pgedge_client_cert` and
  `pgedge_client_key`, or as files on the controller in
  `pgedge_client_cert_src` and `pgedge_client_key_src`. The role writes them
  to `/etc/pki/pgedge` on RHEL-based systems or `/etc/pgedge` on Debian-based
  systems, and `pgedge-subscription-manager` enables the repositories. See
  [Cluster Configuration](../configuration/cluster.md#pgedge_client_cert).
  (#59)

    Without a certificate and key, the role warns and leaves the repositories
    disabled, because an enabled repository the host cannot authenticate to
    makes every package operation fail. Setting `repo_url` removes
    `pgedge-release`, so no certificate is installed then.

### Changed

- `setup_pgedge` reads every zone's Spock state before it creates anything,
  and stops when the inventory does not match the cluster. A run stops when a
  zone that is not yet a member of a cluster holding data is not named in
  `pgedge_join_zones`, when the member zones are not all subscribed to each
  other, or when a zone cannot be read. Adding a database and joining a zone
  take separate runs. A recovery with `pgedge_seed_zone` goes on as before.
  See
  [Why an Ordinary Run Refuses a New Zone](../add_zone.md#why-an-ordinary-run-refuses-a-new-zone).
  (EE-45)
- `setup_pgedge` recognizes an existing subscription by the zone it comes
  from as well as by its name, so it never creates a second subscription from
  the same zone. (EE-45)
- `pgedge_seed_zone` is documented as recovery-only, and a run refuses it
  together with `pgedge_join_zones`. `pgedge_seed_stall_minutes` and
  `pgedge_seed_max_hours` now also limit a joining zone's copy. (EE-45)
- `install_repos` downloads the `pgedge-release` package and the RPM signing
  key from `downloads.pgedge.com`, which needs no certificate, instead of
  `apt.pgedge.com` and `dnf.pgedge.com`. On Debian-based systems it also
  installs `openssl`. (#59)
- The Simple Cluster and Ultra-HA workflows need the `PGEDGE_REPO_CLIENT_CRT`
  and `PGEDGE_REPO_CLIENT_KEY` secrets, and stop before deploying when either
  is empty. (#59)

### Fixed

- A database added to `db_names` now reaches a running cluster when the
  deployment playbook runs again. Every node gets the database, the Spock and
  Snowflake extensions, `pg_hba` rules that name it, and subscriptions to
  every other zone. (EE-44)

    Previously an Ultra-HA cluster whose leaders had moved off each zone's
    first node failed, because `setup_postgres` tried to create the database
    on a replica. With the leaders in place, Patroni was not reloaded, so the
    database stayed closed to subscriptions arriving through the other zones'
    proxies. A simple cluster had the same gap when the new database left the
    pool sizes unchanged.

- Removing a database from `db_names` no longer shrinks the worker and slot
  pools below what the running cluster still uses. The collection never drops
  the database or its Spock objects, so smaller pools left Spock short of
  workers after the next restart, and could stop Postgres from starting. The
  calculated sizes now only go up; setting them in `pg_parameters` still
  overrides them. See [Sizing Floor](../roles/role_config.md#sizing-floor).
  (EE-44)

- The configuration reference explains what removing a name from `db_names`
  does, and how to retire a database before removing its name. See
  [Removing a database from db_names](../configuration/cluster.md#removing-a-database-from-db_names).
  (EE-44)

- `max_worker_processes` counts the Spock manager worker in `coldfront_db`
  where ColdFront is enabled outside mesh mode. The cluster was one worker
  short. (EE-44)

- `setup_patroni` reloads Patroni on a running node whose `patroni.yml`
  changed, and waits for the zone's leader wherever it is, rather than for the
  first node. (EE-44)

- `setup_postgres` no longer edits `pg_hba.conf` or `postgresql.conf` on a node
  Patroni manages. It rewrote Patroni's `pg_hba.conf` without the proxies'
  access rules, which took effect at the next reload. (EE-44)

- The end-to-end tests add a database to a running cluster and take it back
  out of `db_names`, checking replication and pool sizes, after moving each
  Ultra-HA zone's leader to its second node. (EE-44)

- Running the deployment playbook a second time against a deployed cluster
  reports no changes. Previously every run reported several on each pgEdge
  node, which hid any real change among them. These reported a change on
  every run (EE-49):

    - Spock's node and subscription tasks, whether or not they created
      anything.
    - The wait for a zone's Patroni leader.
    - Each `pg_hba.conf` rule, even when the file came out the same.
    - On Debian, the mode of the configuration directory in `/etc/postgresql`,
      which `setup_postgres` and `pg_createcluster` set differently.
    - In SSH mode, the `known_hosts` entries between backup servers and pgEdge
      nodes, which came from `ssh-keyscan` in a varying order. They now come
      from the facts the deployment gathers.
    - Refreshing the APT cache.

- A changed `pgedge_password`, `replication_password` or `backup_password`
  now reaches `.pgpass`. Entries were only ever appended, and libpq uses the
  first that matches, so Spock's subscriptions failed to authenticate the next
  time they reconnected. The new `pgpass_entry` task file in `role_config`
  replaces the entry, and escapes colons and backslashes as `.pgpass`
  requires. (EE-49)

- On a simple cluster with a backup repository, `setup_postgres` writes the
  backup server's `pg_hba.conf` rules. `finalize_backrest` added them after
  `setup_postgres` had rebuilt the file, so each run removed and restored
  them, refusing the backup server in between. (EE-49)

- Every Ultra-HA node has the replication user's `.pgpass` entry, rather than
  only the zone's primary. (EE-49)

- Steps that took a zone's first node for its primary now use
  `zone_primary`, so a run after a failover or switchover behaves as one
  before it (EE-49):

    - The backup server reads the cluster's timeline from the primary. A
      replica can report the old timeline for a while after a failover, which
      made the run take a needless full backup and, with `full_backup_count`
      at 1, expire the previous one.
    - The check that a repository does not already hold the cluster runs on
      the primary. On the first node, it refused a replica wiped for Patroni
      to clone again.
    - `finalize_backrest` checks the repository's identity and points Patroni
      at the repository from the primary.

- `setup_patroni` forces a restart of a first node only when it bootstraps
  the zone. A first node rejoining as a replica restarts only when it has a
  restart pending and `pg_allow_restart` allows it. (EE-49)

- `recover_postgres` can restore a cluster whose worker or connection pools
  grew after the backup it restores. Postgres refuses to replay WAL written
  by a server with larger pools than its own, so the restored node now
  replays with `hot_standby` off, where Postgres skips that check, and starts
  with the pool sizes a deployment would give its zone. (EE-49)

- `tests/check-idempotence.sh` runs the whole deployment playbook a second
  time, rather than only the pooler roles, and fails if any task reports a
  change. On Ultra-HA it also runs after the new
  `tests/playbooks/move-leaders.yml` moves each zone's leader to its second
  node. (EE-49)
